# 慢病病例管理小程序技术方案分析

## 请求摘要

基于前面的讨论，整理一版适合中国大陆市场的首版技术方案，重点回答：

- 平台选型应该是什么
- OCR 应该放在本地还是云端
- 是否需要登录系统
- 云端是否需要数据库和文件存储
- 首版开发周期和上线成本大概是多少

## 当前判断

当前最适合的首版方向是：

- 市场：国内
- 终端：微信小程序
- 前端：优先微信小程序原生开发
- 后端：腾讯云 CloudBase
- OCR：腾讯云 OCR API
- 登录：微信登录

## 为什么不是桌面优先

- 用户的病历照片、处方、检查单天然在手机里
- 家属陪诊、候诊、复诊场景更适合手机端即时打开
- 桌面端虽然更适合重整理，但会增加用户操作路径
- 当前首要目标是验证真实使用频率，而不是先做最完整的本地工作台

## 为什么不是 iOS 优先

- 当前没有 iOS 设备，开发和提审成本更高
- 首版仍在验证需求，不适合先承担 Apple 开发者和提审成本
- 微信小程序在国内获取、分享、试用都更轻

## 为什么首版建议原生小程序

- 当前只做微信一个平台，原生开发最直接
- 原生能力最完整，调试资料最多
- 不需要提前为多端复用引入额外抽象层
- 对 MVP 来说，原生开发复杂度更低

备注：

- 如果未来明确要同时做 H5、App、微信小程序，再考虑迁移到 Taro

## OCR 的判断

### OCR 是否是核心能力

是。对病例管理场景来说，OCR 不是可选增强，而是核心能力。

如果没有 OCR，全量病历、检查单、处方需要用户手工整理，长期使用门槛会过高。

### 小程序能不能直接做 OCR

不建议直接在小程序端做完整 OCR。

原因：

- 小程序不适合承载复杂 OCR 模型
- 前端直接调用 OCR 厂商接口会暴露密钥
- 图片、PDF、批量处理更适合放到云端执行

### OCR 是否一定需要 Python

不一定。

如果使用腾讯云或阿里云现成 OCR API，通常只需要：

- 小程序上传文件
- 云函数接收请求
- 云函数调用 OCR API
- 返回或落库存储结果

这个链路使用 Node.js 即可，不强制需要 Python。

只有在后期自建 OCR 服务或部署 PaddleOCR 一类模型时，Python 运行时才更常见。

### OCR 是否放在云上更合适

是，首版更适合放在云上。

原因：

- 成本低于自建 OCR 服务
- 不需要自己维护模型和推理环境
- 云端更适合处理 PDF、多页图片、批量识别
- 识别完成后再把结构化结果返回给小程序即可

## 云端是否需要数据库

建议需要。

不建议的方案：

- 只在本地存所有结果
- 云端仅做一次性 OCR 计算
- 云端不保留任何结构化数据

这个方案的问题是：

- 小程序本地存储不适合作长期病例资料库
- 换手机、清缓存、重装微信后，数据风险很高
- 后续的时间线、用药追踪、摘要、AI 问答都需要结构化数据支撑

更稳妥的方案是：

- 云端短期中转原始文件
- 云端长期只保留结构化结果
- 小程序本地只做缓存，不做唯一数据源

## 原始文件是否必须长期保存在云端

不一定。

建议首版默认策略：

- 上传后进入云存储
- OCR 完成后短期保留原始文件，便于失败重试和人工复核
- 超过设定保留时间后自动清理
- 云端长期保存结构化结果、摘要和时间线数据

可选策略：

- 默认不长期保存原始文件
- 用户手动勾选“保留原文件用于后续复核”

## 登录系统判断

首版建议直接使用微信登录。

最小实现：

- 小程序端 `wx.login()`
- 云函数或后端换取 `openid`
- 使用 `openid` 作为用户主键

这个方案足够支撑：

- 用户自己的资料隔离
- 同一用户下多患者档案
- 后续权限控制和审计日志

首版不建议自建账号密码系统。

## 合规与边界

产品边界建议明确为：

- 个人病历整理
- 长期用药记录
- 就诊资料摘要
- 基于个人资料的辅助问答

当前不建议涉及：

- AI 诊断
- 治疗方案推荐
- 药物调整建议
- 在线问诊平台

原因：

- 医疗健康信息属于高敏感信息，合规要求更高
- 一旦产品表述接近诊断或治疗建议，审核和责任风险都会明显上升

## 首版推荐架构结论

### 前端

- 微信小程序原生开发
- 页面数量控制在 8 到 12 个核心页面内

### 云端

- 腾讯云 CloudBase
- 云数据库存储结构化病例数据
- 云存储中转原始文件
- 云函数处理 OCR 和摘要流程

### OCR

- 优先腾讯云 OCR API
- 阿里云 OCR 可作为备选

### AI

- 首版不做重 AI 问答
- 可先做规则化摘要或轻量 AI 摘要
- 后续在结构化数据稳定后再接资料问答

## 成本假设

按 2026-03-30 查到的官方文档，当前参考信息如下：

- 腾讯云 CloudBase 免费环境可创建 1 个；付费个人版为 19.9 元/月
- 腾讯云 OCR 通用识别类价格为 0.011 元/次起

因此首版成本判断为：

- 开发期：接近 0 到 20 元/月
- 小流量验证期：20 到 60 元/月较常见
- 有一定使用量后：100 到 200 元/月仍然可控

注意：

- 以上仅为云侧和 OCR 粗估，不含你自己的时间成本
- 小程序类目、备案、主体认证等上线成本需在提审前单独核实

## 主要风险

- 医疗相关类目和审核边界判断失误
- OCR 识别效果对复杂病历格式不稳定
- 用户对隐私和云端存储敏感
- 首版范围失控，过早加入复杂 AI 问答
- 在没有真实用户前，过早投入支付、广告或多端支持

## 当前建议

先做一个非常克制的 MVP：

- 微信登录
- 患者档案
- 病历图片/PDF 上传
- OCR 识别
- 人工修正
- 病例时间线
- 用药记录
- 就诊摘要

在这个基础上验证：

- 用户是否愿意上传真实资料
- 用户是否愿意长期维护
- 用户是否在复诊前反复打开

当这三个问题得到正反馈后，再考虑 AI 资料问答、计费方式和更长期的产品形态。
