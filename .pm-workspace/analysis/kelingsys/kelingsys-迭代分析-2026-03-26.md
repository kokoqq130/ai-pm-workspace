# Requirement Brief

## Request

用户希望基于当前仓库里的旧项目，判断后续应该怎么迭代。

## Business Goal

不是单纯回顾旧代码，而是找出：

- 这个项目现在到了哪个阶段
- 最值得继续投入的方向是什么
- 下一轮应该先修什么、再做什么

## Target Users

- 主要用户：当前用户自己
- 次要用户：医生、家属协作者、需要快速看资料的人

## Current State

基于仓库内容和实际验证，当前状态如下：

### 已确认的能力

- 项目定位清晰，是“查询优先、本地优先、文档驱动”的医疗资料查询系统
- 后端使用 Python + SQLite + FastAPI，前端使用 React + Ant Design
- 已经实现总览、时间线、用药变化、住院周期、检查结果、文档资料、原始文件、搜索等主要页面
- 项目支持开发模式和静态分享模式
- 后端测试已通过：`app/backend` 下 9 个测试全部通过

### 已确认的问题

- 前端当前无法重新构建
- `pnpm run build` 失败
- `pnpm run build:share` 失败
- 当前失败核心信号集中在：
  - `react-router-dom` 版本与现有代码写法存在兼容断裂
  - TypeScript 严格模式下还有一批隐式 `any` 问题

### 关键判断

这个项目不是“要不要继续做”的阶段，而是“该先做稳定化，还是直接继续扩功能”的阶段。

## Desired Change

希望下一轮迭代后，这个项目能做到：

- 本地模式可持续开发
- 分享模式可稳定生成并发布
- 查询体验继续增强，而不是只停留在现在的 MVP
- 后续每次补资料时，不会因为构建链路或依赖漂移而卡住

## Scope

本轮分析聚焦：

- 当前产品阶段判断
- 代码和能力完成度判断
- 后续 1 到 3 个阶段的迭代建议

## Non-Goals

- 本轮不直接进入多患者产品化设计
- 不直接进入复杂录入后台设计
- 不直接进入 AI 医疗建议生成
- 不把它改造成通用 SaaS 再来反推现在怎么做

## Reference Projects

- 当前旧项目本身：`projects/kelingsys`
- 对应产品方案目录：`projects/kelingsys/产品方案/`

## Constraints

- 项目当前强绑定单资料目录 `柯灵用`
- 项目高度依赖本地文件作为事实来源
- 前端构建基线当前失效，会影响开发和分享发布
- 当前自动化验证偏后端，前端回归保护较弱

## Open Questions

- 你后续是想把它继续作为“自己长期使用的资料查询台”，还是想逐步做成“可复用的通用产品”
- 你接下来更重视“医生沟通分享”还是“自己内部整理效率”
- 你是否真的需要多患者/多档案能力，还是单患者深挖就够

## Risks

- 如果在不修构建基线的情况下继续加功能，后面每次发布都会更痛苦
- 如果过早做通用化，会把现在已经很贴合场景的结构打散
- 如果静态分享搜索能力不增强，资料量继续变大后查询体验会明显下降
- 如果前端没有最基本的回归保护，视觉和交互层会越来越难稳定

## Recommended Next Step

推荐先走“稳定化 + 查询增强”路线，而不是产品大转向。

### 建议结论

这个旧项目后续最合理的主线是：

1. 先修复前端构建和分享构建基线
2. 再增强搜索、筛选、资料刷新与结构化查询体验
3. 最后再决定要不要走通用化、多患者或 RAG 问答方向

### 为什么不是先做更多新功能

- 产品骨架已经成形，主要页面也基本齐了
- 真正卡后续迭代的，不是“缺一个页面”，而是“基线不稳”
- 一旦构建和分享不可持续，这个项目就很难继续沉淀

### 当前阶段判断

更准确地说，这个项目现在处在：

- 已完成查询型 MVP
- 正在进入“稳定化 + 产品化可持续”阶段

而不是：

- 纯探索期
- 从 0 到 1 的功能定义期
- 立即做通用平台化的阶段

## 补充分析：从自用工具到商业产品，哪些要改

基于用户补充背景，当前项目原始成立方式是：

- 服务对象一开始就是自己家里人
- 数据录入方式依赖 `Codex + VS Code + AI` 直接读资料、改 markdown、再转结构化数据
- 最终对外展示主要依赖单页应用 + 编译期导出静态 JSON

这套方式对“自己用”很合适，但如果要走向“其他人也能用”或“商业产品”，需要重新区分两层能力：

### 第一层：内部生产流程

这是你自己已经验证有效的部分：

- AI 辅助识别资料
- AI 协助改写 markdown
- markdown 再进入索引和结构化层

这层**不是没有价值**，而是更适合作为：

- 你的内部运营工具
- 高质量数据整理管道
- 初期人工服务 + AI 辅助的交付后台

它的问题不在于“不能存在”，而在于“不能直接要求商业用户自己这么用”。

### 第二层：用户可直接使用的产品流程

如果面向商业用户，用户真正期待的是：

- 上传资料
- 系统自动处理或半自动处理
- 看到结构化结果
- 查询、分享、追溯

也就是说，商业产品不应该暴露：

- VS Code
- Codex 对话式改文件
- 手动维护 markdown 文件树

因此，**要改的是用户入口和交付方式，不一定是整套数据处理思路本身。**

## 对“是不是得大改造”的判断

结论不是“全部推倒重来”，而是：

### 需要大改的部分

1. **数据录入方式**
   - 现在的录入方式是“专家型工作流”
   - 商业产品需要“普通用户可完成的上传与校正流程”

2. **服务架构**
   - 当前静态导出模式更像“快照分享”
   - 商业产品需要至少有一个真正的后端服务承担：
     - 用户身份
     - 数据隔离
     - 文件存储
     - 异步解析
     - 索引更新
     - 历史版本

3. **多租户与权限模型**
   - 当前项目本质是单患者、单资料目录
   - 商业化后至少要支持：
     - 多用户
     - 多档案
     - 权限边界
     - 分享控制

4. **合规与风险控制**
   - 如果处理真实医疗资料，就不能只把它看成普通文档工具
   - 后续至少要补：
     - 审计日志
     - 权限和访问控制
     - 数据删除与导出能力
     - 敏感信息保护策略

### 不一定要推翻的部分

1. **文档驱动 -> 结构化索引** 这条主思路
   - 这是当前项目最有价值的资产之一

2. **查询优先**
   - 这个定位商业上依然成立
   - 很多人真正缺的不是“录入后台”，而是“资料整理后怎么查得快、讲得清、能追溯”

3. **静态分享能力**
   - 它不适合当主服务架构
   - 但很适合继续保留为：
     - 医生沟通快照
     - 个案导出包
     - 对外只读分享模式

4. **你现在的 AI 整理流程**
   - 不适合作为终端用户工作流
   - 但非常适合作为早期“运营后台”和“高质量人工兜底流程”

## 更适合的演进路径

比起直接做“商业 SaaS 重构”，更合理的是分三段：

### 阶段 A：继续做强单案例产品，但把它定义成“运营可交付系统”

这时的目标不是让每个用户自己录数据，而是：

- 你或团队帮用户整理资料
- 系统输出高质量查询结果和分享页面

产品形态更像：

- AI 辅助的医疗资料整理服务
- 带查询系统的交付后台

这一步的意义是：

- 保留你当前最强的能力
- 先验证别人是否真的愿意为“整理 + 查询 + 沟通”买单
- 不急着承担完整 SaaS 的技术成本和合规成本

### 阶段 B：把录入流程产品化，但仍允许人工兜底

这时开始增加：

- 文件上传
- OCR / 解析任务队列
- AI 抽取后的人工确认
- 档案级数据管理

这一步的目标不是“完全自动”，而是：

- 用户能自己完成 60% 到 80% 的录入
- 剩下复杂部分仍可人工介入

### 阶段 C：再决定要不要做完整云产品

只有在下面这些信号成立后，才适合进入这一步：

- 已经有明确付费用户或强需求用户
- 已经验证不是只适合你自己这一类高参与度场景
- 已经知道最常见的资料类型和高频查询路径
- 已经确认愿意承担长期云服务、权限、合规和运维成本

## 关于“后端数据库编译成 JSON 静态文件”是否一定要改

如果目标是商业产品主架构，答案是：**大概率要改。**

但如果目标是“早期商业验证”，答案是：**不一定要立刻改掉。**

### 静态导出仍然适合的场景

- 单个家庭或单个档案的只读分享
- 医生沟通包
- 周期性快照
- 人工整理后的交付结果

### 静态导出不适合承担的场景

- 多用户实时登录
- 在线持续更新资料
- 用户自己上传后马上处理
- 权限细粒度控制
- 大规模搜索与多租户隔离

所以更准确的处理方式是：

- **不要把静态导出当主服务架构**
- **但要把它保留成一个很有价值的导出模式**

## 当前最合适的策略建议

基于你现在的起点，我更建议：

### 不要现在直接做“大而全的商业重构”

因为那样会同时踩中：

- 架构重构
- 录入重构
- 权限重构
- 合规重构
- 产品定位重构

风险太集中。

### 更建议做“双轨策略”

#### 轨道 1：保留并强化现在这套“内部整理引擎”

包括：

- AI + markdown 的高质量整理流程
- 索引与结构化抽取
- 查询与静态分享

#### 轨道 2：单独定义“面向外部用户的产品壳”

优先补：

- 上传入口
- 档案管理
- 后端服务
- 用户隔离
- 审核/确认流程

这样做的好处是：

- 你不会把当前已经验证过的方法论直接扔掉
- 商业化新增复杂度被限制在“用户入口层”和“服务层”
- 你的内部流程还能继续作为高质量兜底能力

## 补充分析：如果核心价值是“报告识别 -> AI 分析 -> 病案生命周期生成”，token 怎么处理

基于用户最新补充，真正最有价值的能力不是“静态查询页”本身，而是：

- 识别用户上传的检查报告、住院资料、化验单、病历
- 用 AI 做抽取、归纳、关联
- 最终生成一个可持续更新的病案生命周期

这件事是有产品价值的，而且比传统让用户自己填大量表单更自然。

但这里最大的风险之一，确实就是模型 token 成本。

### 先给结论

token 问题**不能靠一句“换便宜模型”解决**。

更合理的做法是：

1. 把 AI 处理拆成多层流水线
2. 让昂贵模型只处理少量高价值环节
3. 把大部分查询成本转成预计算和缓存
4. 定价时不要按“无限使用”承诺

换句话说，token 成本本质上是**系统设计问题 + 商业模型问题**，不是单纯的 API 采购问题。

## 哪些环节最烧 token

如果按当前想象去做，最容易失控的通常有三块：

### 1. 直接把整份病历 / 全部报告反复丢给模型

这会导致：

- token 随历史资料增长线性甚至超线性增加
- 每次新增一份报告都要重复消费旧上下文
- 越到后期越贵

### 2. 把 OCR、分类、抽取、总结全部交给同一个大模型

这会导致：

- 本来可以便宜处理的环节，也被高价模型吃掉
- 多页 PDF / 图片尤其贵

### 3. 每次用户查询都重新“理解整份档案”

这会导致：

- 查询次数越多，成本越不可控
- 商业上很难做稳定毛利

## 更合理的 token 控制思路

### 一、把处理流程拆成 5 层

#### 第 1 层：资料接入层

负责：

- 上传 PDF、图片、截图、病历文档
- 文件去重
- 页数统计
- 基础元数据提取

这一层尽量不用大模型。

#### 第 2 层：OCR / 文本获取层

负责：

- 图片/PDF 转文本
- 表格和版面初步识别

原则：

- 优先用 OCR 或专用文档解析能力
- 不要默认每页都走高成本通用大模型视觉理解
- 只有 OCR 失败或版式复杂时，才升级到更贵的视觉模型

#### 第 3 层：轻量分类与结构化抽取层

负责：

- 这是检验报告、住院记录、处方还是病程记录
- 提取日期、指标名、数值、单位、药物、事件、诊断等字段

原则：

- 先按“单文档 / 单页 / 单 chunk”抽取
- 输出 JSON
- 加置信度
- 低置信度进入人工确认或升级模型

这里可以使用更便宜的模型或规则系统，不要直接上最贵模型。

#### 第 4 层：病例图谱 / 生命周期合并层

负责：

- 把新的抽取结果并入现有病例
- 更新时间线
- 更新指标趋势
- 更新住院周期
- 更新当前治疗方案

这一层最好尽量规则化、数据库化，而不是每次都让模型“重新理解全部历史”。

核心思想是：

- **增量更新**
- **事件化存储**
- **结构化归并**

#### 第 5 层：高价值摘要与问答层

负责：

- 生成医生沟通摘要
- 生成某次住院总结
- 生成“当前病情概览”
- 做带引用的问答

这时才值得调用更强的模型，因为它直接面向用户价值。

## 一个很关键的产品原则

### 不要让“查询”变成主要 token 消耗点

商业上更合理的是：

- 上传时花一次较重成本做整理
- 查询时主要读取结构化结果、摘要和引用

也就是说，应该尽量让成本结构变成：

- **高价值的一次性整理成本**
- **低成本的重复查询成本**

而不是反过来。

## 最推荐的架构策略

### 1. 建立“摘要金字塔”

不要只存原文和最终结论，中间要多存几层：

- 原始文件
- OCR 文本
- 文档级摘要
- 事件级结构化结果
- 住院周期摘要
- 病例总览摘要

好处是：

- 查询时不用反复吃原文
- 更新时只重算受影响的层
- 生命周期越长，越省 token

### 2. 做“增量处理”，不要做“全量重算”

每次新增报告时，理想方式应该是：

- 只处理新增文件
- 只更新相关住院周期或指标
- 只重写受影响的摘要

而不是：

- 把整个病例重新喂给模型

### 3. 以“字段抽取 + 引用”替代“纯大段自由生成”

自由生成最贵，也最不稳定。

更建议：

- 先抽取结构化字段
- 再根据结构化字段生成短摘要
- 所有结论都能回链到原文或原图

### 4. 把模型做成“分级路由”

例如：

- 简单标准化报告 -> 低成本模型或规则
- 普通住院记录 -> 中等模型
- OCR 很差、版式复杂、跨文档推理 -> 高成本模型

不是所有任务都值得走最强模型。

### 5. 低置信度时，优先人工校正，而不是无限追加推理

很多团队会陷入一个坑：

- 模型第一次没抽准
- 就继续加 prompt、继续追问、继续叠 token

这在商业上非常危险。

更合理的是：

- 超过预算阈值后，直接进入人工确认
- 人工修一次，后面长期复用

## 商业化时，token 成本怎么定价

最不建议的是：

- “一个月固定订阅，AI 无限跑”

这几乎一定会出问题。

更建议的定价单位是：

- 按档案
- 按页数
- 按上传批次
- 按整理次数
- 按高级摘要/医生报告次数

也就是卖：

- “一次整理能力”
- “持续维护能力”
- “高价值输出能力”

而不是卖抽象的 token。

## 你应该盯的成本公式

更适合内部管理的不是“总 token”，而是：

### 单档案成本

`单档案成本 = OCR 成本 + 结构化抽取成本 + 生命周期合并成本 + 摘要生成成本 + 查询成本`

### 单次新增资料成本

`单次增量成本 = 新页数处理成本 + 新事件合并成本 + 受影响摘要重算成本`

### 单次查询成本

理想目标是把它压到很低，因为查询会高频发生。

## 对这个方向的产品判断

如果你走的是“AI 帮用户把资料自动整理成病案生命周期”，那它是值得做的，而且比“让用户自己填很多内容”更有机会。

但要成立，必须满足两个条件：

### 条件 1：token 成本必须被架构吃掉，而不是被用户对话次数放大

也就是：

- 多做预处理
- 多做增量更新
- 多做缓存
- 少做全量重理解

### 条件 2：商业定价必须对齐成本结构

也就是：

- 不卖无限
- 卖整理、维护、输出这些高价值动作
- 高复杂度案例允许人工兜底或高阶套餐

## 基于当前阶段的最合适处理建议

如果你把这个能力当成未来的商业核心，我建议现在就按下面这个方向演进：

### 产品内核

- 报告识别
- 结构化抽取
- 生命周期生成
- 医生沟通摘要

### 成本控制原则

- OCR 和文档理解前置
- 大模型只做高价值判断
- 结果持久化
- 查询尽量不重跑大模型

### 商业落地路径

- 先做“AI 辅助病案整理服务”
- 再做“半自动上传 + 确认”
- 最后再做“自助式云产品”

这条路比直接做一个“用户自己随便上传，系统无限帮他理解所有历史资料”的产品要稳得多。

## 补充分析：如果做成移动端优先的工具版，是否合适

用户当前进一步提出两点：

- 想重点做移动端
- 希望工具版尽量不依赖自己建设云端服务

### 结论

**可以做，但更适合“移动端优先”，不适合“只有移动端”。**

### 为什么移动端值得优先

对于这个产品方向，移动端在几个环节天然更强：

- 用户拍报告、上传 PDF、补充资料，通常第一现场就在手机上
- 用户随手查看当前病案摘要、某次住院、某个指标趋势，也更常发生在手机上
- 医生沟通时快速打开资料和分享链接，移动端价值很高

所以从“采集入口”和“消费入口”看，移动端优先是合理的。

### 为什么不建议只有移动端

但如果涉及下面这些重任务，移动端会明显吃亏：

- 大批量资料导入
- 复杂报告纠错
- 生命周期结构校正
- 长时间 OCR / 抽取 / 汇总
- 专业人员逐条确认抽取结果

也就是说：

- **移动端适合上传、查看、确认**
- **桌面端或平板更适合重度整理和运营**

如果你完全砍掉大屏入口，后面会限制产品上限。

### 更好的产品形态

更推荐的是：

- **移动端优先**
- **桌面端可选**

而不是：

- 只做网页静态页
- 或只做纯桌面工具

## “没有任何自建云端服务也能跑起来”这件事，怎么理解更准确

### 从存储和索引角度

是的，**可以不依赖你自己的云端服务**。

你完全可以把下面这些都放在本地：

- 原始文件
- 本地数据库
- 本地缓存
- 本地摘要
- 本地时间线和结构化结果

从技术上看，这条路是成立的。

### 从 AI 调用角度

这里要分清楚：

- **没有你的云服务**
- 不等于
- **完全没有网络依赖**

如果用户自己提供第三方模型 API key，那么应用依然需要联网去调用模型提供商。

所以严格说，真正可能成立的是：

- **无自建云**
- **但有外部模型网络请求**

而不是：

- 完全离线 AI

除非你后面改成端侧模型，那又是另一条路线。

## 关于 BYOK 在移动端的关键风险

如果你走的是“用户自己维护自己的 AI API key”，有一个非常重要的限制：

### 对 OpenAI 这类 API，官方并不建议把 key 用在移动端客户端直连

OpenAI 官方 API 文档和帮助中心都明确强调：

- 不要把 API key 暴露在客户端代码中
- 不要在浏览器或移动 app 里直接部署 key
- 请求更推荐通过自己的后端转发

这意味着：

- **技术上能做**
- **但不是官方推荐的生产安全架构**

所以如果你坚持无自建云 + 移动端 + BYOK，这条路更适合：

- 早期工具版
- 专业用户版
- 明确告知风险的自助版

而不适合作为长期默认的“面向大众的标准版”。

## 如果仍要做移动端 BYOK 工具版，更合理的边界

### 可以接受的定位

- 个人工具
- 专业版工具
- 隐私优先版工具
- 早期验证版产品

### 不适合过度承诺的定位

- 面向大众小白用户的零门槛产品
- 完全托管、安全无感知的标准 SaaS

## 移动端工具版最合理的职责划分

### 手机负责

- 拍照/上传
- 查看病案摘要
- 查看时间线
- 查看某次住院和指标趋势
- 对低置信度结果做轻量确认
- 导出分享包

### 大屏端负责

- 大批量资料整理
- 长文本核对
- 复杂抽取纠错
- 运营后台和人工兜底

## 对产品路线的影响

如果你决定做移动端优先工具版，我建议不要把第一版定义成：

- “纯移动端、纯客户端、面向所有人”

更建议定义成：

- “移动端优先的 BYOK 专业工具”

这样你就能把预期对齐：

- 它不是零门槛大众产品
- 它更像高参与度用户的专业工具
- 它可以先不依赖你的云服务
- 但后面如果验证成功，仍然保留升级到托管版的空间
