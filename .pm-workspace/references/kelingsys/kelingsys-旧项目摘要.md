# Reference Project Snapshot

## Source

- Project: `projects/kelingsys`
- Repo or doc link: 当前工作区挂载旧项目仓库
- Owner: 当前用户
- Why it matters now: 用户想判断这个旧项目下一步该怎么迭代

## Comparable Flow

这个项目本身就是当前要分析的旧项目，核心流程是：

- 以项目内 markdown、图片、PDF 作为事实来源
- 用 Python + SQLite 建立索引
- 用 FastAPI 提供查询接口
- 用 React + Ant Design 提供总览、时间线、用药、住院周期、检查结果、文档和原始文件查询
- 同时支持本地开发模式与静态分享模式

## Reusable Decisions

- 明确坚持“查询优先”，而不是再做一套复杂人工录入后台
- 数据源直接复用项目内真实文件，不要求重复录入
- 后端索引层与前端展示层分开，便于后续继续增强结构化抽取
- 静态分享模式已经具备方向正确的产品化价值，适合医生沟通和对外轻量分享
- 住院周期、检查分组、原始资料回溯已经形成了比较明确的产品骨架

## Constraints Found There

- 当前实现仍然是单患者、单资料目录模型，`DATA_ROOT` 直接指向 `柯灵用`
- 前端依赖与源码存在兼容断裂，当前 `pnpm run build` 与 `pnpm run build:share` 无法通过
- 静态模式下搜索仍然是前端本地 `includes` 过滤，随着资料增加会变得更弱
- 当前测试主要覆盖后端索引与查询，前端缺少自动化回归保护

## Things To Avoid

- 不要现在就把方向切成“多患者 SaaS”或“通用医疗后台”
- 不要在构建基线失效时继续叠加新页面和新功能
- 不要把静态分享模式当成一次性副产物，它已经是这个项目的重要能力
- 不要反过来引入复杂手工录入流程，和项目原始定位冲突

## Follow-Up

目前摘要已经足够支持下一步迭代判断，不需要继续额外挂载新仓库。后续如果要进入“通用化、多患者、RAG 问答”方向，再补充新的参考材料更合适。
