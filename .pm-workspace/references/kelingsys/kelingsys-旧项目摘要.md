# kelingsys 旧项目摘要

> 生成时间：2026-03-30  
> 摘要来源：基于已挂载项目 `projects/kelingsys/` 的目录结构、产品方案、前后端代码与项目规则整理

## 一句话定位

`kelingsys` 不是通用型业务系统，而是一个围绕单一患者医疗资料建立的“资料整理 + 查询管理系统”项目。

它同时包含两条主线：

- 资料整理主线：持续维护主病情文档、住院整理文档、OCR 报告、报告重命名与 PDF 导出
- 系统开发主线：把现有 markdown、图片、PDF 等资料建立索引，做成一个查询优先的前后端系统

## 项目当前想解决的问题

这个项目想解决的不是“复杂后台录入”，而是“已有医疗资料太分散，不方便查询、回溯和给医生快速理解”的问题。

当前方案是：

- 继续保留人和 AI 协作更新 markdown 文档的工作方式
- 用程序把真实资料文件做索引和结构化抽取
- 提供总览、时间线、搜索、检查结果、文档预览、原始资料跳转等查询能力

## 技术栈摘要

### 前端

`app/frontend/package.json` 显示前端技术栈为：

- React 19
- Vite 7
- TypeScript 5.9
- Ant Design 6
- `@ant-design/x-markdown`

- `react-router-dom` 7

这和项目 `AGENTS.md` 中“系统开发模式”的约束是一致的，说明前端已经按 Ant Design 生态统一推进。

### 后端

`app/backend/` 当前是：

- FastAPI
- Uvicorn
- SQLite 索引库
- PaddleOCR / PaddlePaddle

其中：

- `main.py` 暴露查询 API
- `services/indexer.py` 负责扫描资料、重建索引、抽取结构化数据
- `services/query_service.py` 负责总览、时间线、搜索、住院详情等查询逻辑

## 数据与索引方案摘要

这个项目最值得关注的，不是 UI，而是它的数据组织方式：

### 1. 数据源直接来自真实资料文件

后端配置里把数据根目录直接指向：

- `柯灵用/`

索引库写入：

- `data/index.db`

### 2. 索引扫描的文件类型明确

当前扫描：

- `.md`
- `.jpg`
- `.jpeg`
- `.png`
- `.pdf`

### 3. 文档分类规则已经写死到业务语义里

目前后端会把 markdown 文档分成：

- 主文档 `main_summary`
- 住院整理 `admission_note`
- 出院小结 `discharge_summary`
- 报告索引 `report_index`

### 4. 已经做了结构化抽取

当前索引过程会抽取：

- 事件时间线
- 住院周期
- 当前与历史用药
- 检查结果
- 总览摘要
- 文档与原始文件引用关系
- 全文搜索索引（FTS）

这意味着它不是简单的文件浏览器，而是“文档驱动的轻量医疗知识检索系统”。

## 产品思路里的关键决策

这个旧项目有几条非常明确、而且很值得复用的产品决策。

### 1. 查询优先，而不是录入优先

项目 `AGENTS.md` 明确写了：

- 查询管理系统是“查询优先”，不是“表单录入优先”

这是一条很有价值的判断。对于资料型项目，先把“查得到、看得懂、回得去原文件”做出来，往往比先做复杂录入后台更有效。

### 2. 保留 markdown 作为主事实来源

项目没有把所有信息都强行搬进数据库，而是：

- 继续把 markdown / 图片 / PDF 作为核心资料源
- 再由索引层提取出查询所需的结构化结果

这是低成本、可持续、适合 AI 协作的路线。

### 3. 原始资料可回溯

无论是设计文档还是后端接口，都强调：

- 查询结果最终要能跳回原文档或原图

这对医疗类资料尤其重要，因为用户需要验证来源，而不是只看系统二次加工后的摘要。

### 4. 支持“开发模式 + 静态分享模式”

`app/README.md` 里已经明确：

- 开发模式：前后端接口模式
- 分享模式：导出静态 JSON 和原始资料，构建分享站点

这个思路很实用，说明项目已经考虑到“不是所有场景都适合长期部署 Python 服务”。

## 当前项目的局限与风险

如果后续要继续做迭代，这些限制需要重点注意。

### 1. 领域绑定非常强

当前项目强绑定到单一对象和固定目录命名，例如：

- `柯灵用/`
- `柯灵基本信息.md`

这对于当前场景很高效，但如果后续想泛化成“多患者 / 多项目 / 多家庭成员”系统，现有命名和规则会成为阻力。

### 2. 结构化抽取规则偏手工和规则化

`indexer.py` 里有明显的领域硬编码，例如：

- 文档分类规则写死
- 已知药物名称列表写死
- 指标与文本判断规则写死
- 中文描述模式解析写死

这说明当前索引器对现有资料格式适配度高，但扩展到更多文档类型时维护成本会上升。

### 3. 隐私与分享边界需要谨慎

这个项目的资料明显包含患者隐私信息。

虽然已经设计了静态分享模式，但如果后续继续做分享能力，必须严格区分：

- 内部整理版
- 可对外分享版
- 是否脱敏
- 原始资料是否可直接访问

### 4. 目前更像“单项目垂直工具”，不是平台型产品

从目录、规则、字段抽取和页面设计看，它目前适合一个明确对象的长期资料管理，而不是通用 SaaS。

如果未来要平台化，很多规则都要抽象重构。

## 这个项目最值得复用的部分

如果以后你拿这个旧项目做新需求判断，最值得复用的是下面几类能力：

### 可以直接复用的思路

- 查询优先的产品策略
- 文档驱动的数据组织方式
- 原始资料可回溯的设计原则
- 静态分享与本地开发双模式
- AI 协作维护文档 + 系统做索引查询的组合方式

### 可以参考但不应原样复制的部分

- 规则型结构化抽取逻辑
- 面向当前患者命名的目录结构
- 强绑定单对象的文档分类约定

这些适合作为第一版实现参考，不适合不加抽象地直接搬到新项目。

## 对后续迭代判断的价值

如果后面你要分析“这个旧项目应该继续做什么迭代”，这份旧项目摘要可以先支持下面几类判断：

- 这个项目当前更适合继续做深度查询，还是做录入后台
- 是否应该从单患者工具扩展成多对象资料平台
- 是否应该加强脱敏分享能力
- 是否应该把规则型索引逐步抽象成更通用的数据提取层
- 是否应该继续深化移动端查询体验

## 当前结论

`kelingsys` 是一个已经有明确产品思路、资料治理方式、前后端原型和本地 AI 协作规则的垂直项目。

它的核心价值不在“花哨功能”，而在下面这条路线已经被验证：

- 用 AI 和 markdown 持续维护真实资料
- 用索引层从真实资料中抽取查询能力
- 用轻量前后端提供总览、回溯、搜索和趋势查看

所以后续如果基于它继续迭代，优先应该围绕：

1. 查询体验增强
2. 索引抽取稳定性提升
3. 分享 / 脱敏边界完善
4. 是否需要泛化为多对象模型

而不是一上来就重做成重后台、重录入、重流程的平台型系统。
