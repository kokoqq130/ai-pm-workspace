# kelingsys 后续迭代建议

## 总判断

推荐继续迭代，但不要把下一步理解成“再堆几个页面”。

这个项目现在最适合继续沿着下面这条主线推进：

**先修基线，再增强查询，再决定是否通用化。**

## 结论一句话

短期内，把它当成一个“单患者、高可追溯、可分享的资料查询系统”继续做最值。

## 推荐路线

### 第一阶段：P0 稳定化

目标：把它恢复成一个可以持续开发、可以持续分享发布的项目。

优先做：

1. 修复前端构建失败
   - 统一 `react-router-dom` 版本与当前代码写法
   - 修掉 TypeScript 严格模式下的隐式 `any`
   - 让 `pnpm run build` 通过
   - 让 `pnpm run build:share` 通过

2. 补最小前端回归保护
   - 至少把“能构建”变成稳定检查项
   - 最少加一层页面级 smoke 校验或 CI 检查

3. 固化分享链路
   - 本地生成分享包要稳定
   - CI 分享发布要能重新可信地跑通

### 第二阶段：P1 查询增强

目标：让这个系统在资料继续增加时，仍然比翻文档更高效。

优先做：

1. 增强搜索
   - 搜索结果支持更好的排序
   - 加入事件类型、文档类型、日期范围等筛选
   - 统一 live/static 两种模式下的搜索体验

2. 增强资料刷新反馈
   - 刷新索引后告诉用户新增了什么、解析了什么、失败了什么
   - 减少“刷新了但不知道有没有生效”的不确定感

3. 增强结构化查询
   - 更好地表达某次住院、某个指标、某次调药之间的关系
   - 补充更多面向医生沟通的快捷入口

### 第三阶段：P2 决定是否扩张

目标：在基线稳定后，再决定要不要把它做得更大。

有两条可选路：

1. 继续深挖单患者版本
   - 更强的趋势图
   - 更强的问答入口
   - 更好的住院周期聚合

2. 再做通用化
   - 配置化数据目录
   - 多患者支持
   - 更中性的命名和 UI 文案

## 当前不建议优先做的事

- 不建议现在就做复杂录入后台
- 不建议现在就做多用户权限体系
- 不建议在构建链路没修好前继续堆功能
- 不建议过早把它改造成通用 SaaS

## 最推荐的下一步动作

如果你要我继续往下做，我建议下一步直接进入：

**修复前端构建与分享构建基线。**

这是当前最值、最不容易后悔的一步。修完以后，这个项目才真正适合继续长期迭代。

## 基于新背景的升级判断

你补充的背景很关键：这个项目最初是给自己家里人用的，自带很强的“专家工作流”特征。

所以现在真正要回答的问题不是：

- “要不要商业化”

而是：

- “商业化时，哪些能力继续保留为内核，哪些必须换成面向普通用户的方式”

## 我的核心判断

### 是，需要改造

但不是“整套系统全部推翻重做”。

### 更准确地说，是需要做一次“产品层重构”，而不是“能力层推翻”

保留的应该是：

- 文档/资料 -> 结构化索引 -> 查询与追溯 这条主链路
- 你现在验证过的 AI 整理方法
- 静态分享作为导出能力

必须改的主要是：

- 用户录入入口
- 后端服务方式
- 多用户/多档案架构
- 权限与合规能力

## 最不建议的处理方式

### 不建议直接一步到位做完整 SaaS

原因很简单：

- 你现在还没验证商业用户是否真的愿意买单
- 你也还没验证他们最愿意付费的是哪一段价值
- 如果现在就重做成完整云产品，投入会非常大，而且很容易做错方向

## 最建议的处理方式

### 走“三阶段演进”

#### 阶段 1：把当前系统定位成“运营后台 + 交付系统”

这阶段不要要求用户自己像你一样用 Codex + VS Code。

更合理的产品定义是：

- 用户把资料交给你
- 你或你的团队用当前 AI 整理流程处理
- 系统输出一个可查询、可分享、可追溯的结果给用户

这一步本质上卖的是：

- 资料整理能力
- 结构化能力
- 查询和医生沟通能力

而不是“卖一个通用软件账号”。

这是最适合你当前起点的商业化方式。

#### 阶段 2：逐步把录入流程产品化

在已经有真实外部用户后，再开始补：

- 文件上传
- OCR / 解析任务
- AI 抽取结果确认
- 档案级管理
- 多用户隔离

这时候你的系统会从“内部专家工具”过渡成“半自动产品”。

重点不是完全自动，而是：

- 用户能自己完成一部分
- 复杂情况仍然可人工兜底

#### 阶段 3：有付费验证后再上完整云产品

只有在你确认下面几件事之后，才值得大改造：

- 已经有持续外部需求
- 已经有明确付费意愿
- 已经知道高频资料类型和高频查询场景
- 已经愿意承担云服务、权限、合规、运维成本

到这个阶段，再重构成真正的商业产品就顺了。

## 对你两个担心的直接回答

### 1. `Codex + VS Code + AI + markdown` 这条录入方式，商业化肯定不行，对吗？

对，**不能作为终端用户工作流**。

但它完全可以继续作为：

- 你的内部生产力工具
- 早期运营后台
- 复杂案例的人工兜底流程

所以不是“废掉”，而是“从用户入口移到运营后台”。

### 2. 现在没有云后端，只能编译成静态 JSON，这块也得改吗？

如果目标是完整商业产品，**要改**。

但如果目标是先做外部验证，**不用马上彻底改掉**。

更合理的做法是：

- 把静态 JSON 继续保留为“交付快照 / 分享包”
- 另外逐步补一个真正的后端服务，负责：
  - 用户
  - 档案
  - 文件存储
  - 解析任务
  - 索引更新
  - 权限控制

也就是说，静态导出不是错，而是不该继续承担主架构。

## 我给你的最终建议

如果你的目标是“以后可能做商业产品”，现在最合适的路线不是：

- 立刻全量 SaaS 化

而是：

1. 先把当前系统修成稳定可交付版本
2. 把它当成“AI 辅助资料整理 + 查询交付系统”去服务少量外部用户
3. 从真实使用里验证：
   - 别人最买单的是整理、查询、分享、医生沟通里的哪一段
   - 哪些资料类型最常见
   - 哪些环节必须产品化
4. 再决定是否进入真正的大改造

## 关于 token 成本，我的直接建议

如果你真正想做的核心是：

- 识别用户报告
- AI 分析资料
- 自动形成病案生命周期

那这方向是有价值的，而且比“让用户自己填很多字段”更有机会。

但这里最重要的一点是：

**不要把 token 成本理解成模型采购问题，要把它理解成产品架构问题。**

## 最关键的一句话

### 不要让模型反复理解整份病例

这是最容易把成本做爆的地方。

正确方向应该是：

- 上传时做增量整理
- 存结构化结果
- 存分层摘要
- 查询时尽量读取已有结果

而不是：

- 每次查询都把全部历史资料再喂一遍模型

## 最推荐的处理方式

### 1. 把 AI 流程拆层

建议拆成：

1. 文件接入
2. OCR / 文本获取
3. 文档分类
4. 字段抽取
5. 生命周期合并
6. 最终摘要 / 问答

其中只有最后两层里的一小部分，才值得用更贵的模型。

### 2. 做增量更新，不做全量重算

新增一份报告时，系统应该只处理这份新资料，并更新受影响的那部分病案。

不要因为多了一张化验单，就重新让模型理解一遍整个人的所有历史。

### 3. 建立“摘要金字塔”

建议长期保存：

- 原始文件
- OCR 文本
- 文档级摘要
- 事件级结构化结果
- 住院周期摘要
- 病例总览摘要

这样 token 会随着系统沉淀越来越可控，而不是越来越失控。

### 4. 用模型分级路由

不是所有任务都上最强模型：

- 简单标准化报告 -> 便宜流程
- 普通住院资料 -> 中等模型
- 复杂跨文档推理 -> 高成本模型

### 5. 低置信度时进入人工确认

不要无限追加 prompt 去硬抠正确率。

商业上更稳的做法是：

- 到预算阈值就停
- 转人工确认
- 把确认结果沉淀下来

## 商业上怎么收费更合理

最不建议的是：

- 一个固定月费 + AI 无限跑

更建议按下面这些单位收费：

- 档案数
- 上传页数
- 整理批次
- 高级摘要次数
- 医生沟通报告次数

也就是卖：

- 整理能力
- 维护能力
- 输出能力

不是卖 token。

## 我对这个方向的判断

如果你要走这条路，我会建议你把产品重新定义成：

**AI 病案整理与病程生命周期生成系统**

而不是：

**单纯的医疗资料查询站**

前者才是你的真正差异化点。

## 现在最适合做的不是

- 先做完整 SaaS
- 先纠结所有模型费用
- 先追求用户自己完全自动完成全部整理

## 现在最适合做的是

1. 先验证这项能力对外部用户是否真的值钱
2. 先把流水线拆分，确认哪个环节最烧 token
3. 先把成本控制在“单档案可接受”范围内
4. 再决定云化和自助化程度

## 如果工具版重点做移动端，我的判断

### 方向是对的

因为这个产品最自然的高频场景本来就在手机上：

- 拍报告
- 上传资料
- 快速看病案摘要
- 医生面前临时查资料
- 把结果分享给家属或医生

所以“移动端优先”是合理的。

### 但我不建议“只有移动端”

原因也很直接：

- 重度资料核对
- 长文本纠错
- 生命周期结构校正
- 大批量整理

这些任务在手机上体验会明显差很多。

所以更合理的产品定义是：

**移动端优先，桌面端可选。**

## 这个工具版能不能没有你的云服务

### 可以，原则上能跑起来

如果你说的是：

- 不要你自己维护后端账户系统
- 不要你自己维护云数据库
- 不要你自己承担模型 token

那这条路是成立的。

你可以做成：

- 本地文件
- 本地数据库
- 本地缓存
- 用户自己提供 API key
- 需要时直接请求模型提供商

### 但要注意一个现实边界

这叫：

- **无自建云**

不等于：

- **完全离线**

只要用了外部模型 API，就还是要联网。

## 这条路最大的限制

如果你用的是 OpenAI 这类 API，官方并不推荐在移动端客户端直接用 API key。

这意味着：

- 早期工具版可以这么做
- 但它更适合专业用户、自助用户、早期验证
- 不太适合作为长期面向大众的标准版安全方案

## 所以我对这个形态的最终判断

### 很适合做第一阶段产品

定义成：

**移动端优先的 BYOK 专业工具**

这会很合理。

### 不太适合直接定义成最终商业形态

因为后面一旦用户量上来，你大概率还是会遇到：

- key 安全
- 用户支持
- 权限和同步
- 档案共享
- 合规和审计

这些问题。

## 最推荐的定位

如果现在就定方向，我建议你把第一阶段产品定位成：

**移动端优先、无自建云、用户自备 key 的 AI 病案整理工具**

同时从一开始就保留未来升级空间：

- 后面可补桌面端
- 后面可补托管后端
- 后面可补标准 SaaS 版
