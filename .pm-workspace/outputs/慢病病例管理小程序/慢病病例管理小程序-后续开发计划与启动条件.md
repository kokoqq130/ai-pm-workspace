# 慢病病例管理小程序后续开发计划与启动条件

## 1. 先给结论

现在可以开始开发，但要分成两种“开始”：

### 1.1 现在就可以开始的部分

- 项目工程初始化
- 页面骨架开发
- 本地类型定义
- 云函数目录和接口骨架
- 设置页与 AI 高级设置页面
- 假数据联调
- 隐私文案、提示文案接入

这些部分不依赖正式云资源，今天就可以开干。

### 1.2 还不能算“正式进入主开发”的部分

以下条件没补齐之前，不建议进入真正的 OCR、数据库和联调主线开发：

- CloudBase 环境已开通
- OCR 服务已可调用
- 数据库安全规则已配置
- 样本资料已准备好

也就是说：

`现在可以开始做前半段开发准备，但还不建议直接冲完整业务闭环。`

## 2. 当前状态判断

结合现有文档，当前状态可以理解为：

### 2.1 已经明确的内容

- 产品范围已基本冻结
- 页面结构已明确
- 数据表设计已明确
- 核心交互已明确
- 隐私边界已明确
- OCR 失败兜底已明确
- LLM 策略已明确
- 用户自定义模型 Key 接入方式已明确

### 2.2 仍未完成的关键前置项

- 腾讯云 CloudBase 未实际开通
- OCR 服务未实际配置可调用
- CloudBase 安全规则未落地
- 真实或脱敏资料样本未准备
- 小程序后台和 AppID 未确认
- Git 仓库与工程规范未实际初始化

## 3. 什么时候可以开始开发

## 3.1 如果你问“今天能不能开始写代码”

可以。

建议今天就开始：

- 初始化小程序项目
- 建立目录结构
- 建 shared types
- 先做登录页、患者列表页、患者详情页、设置页静态骨架
- 建立云函数空壳
- 建本地 mock 数据流

## 3.2 如果你问“什么时候可以开始正式主线开发”

建议满足下面 4 个条件后，正式进入主线开发：

1. CloudBase 环境开通
2. OCR 服务开通并能成功返回测试结果
3. 数据库安全规则配置完成
4. 至少准备好一批最小样本资料

最小样本建议：

- 5 份病历照片
- 5 份检查单
- 5 份处方
- 3 份出院小结
- 2 份 PDF
- 2 份手写或低质量样本

## 3.3 我的判断

如果你这两天能把云资源和样本准备好，那么：

- `今天` 就可以开始工程开发
- `1 到 3 天内` 可以进入正式主线开发

如果云资源和样本准备拖住了，那么：

- 现在先做前端骨架和本地联调
- 等资源补齐后再接真接口

## 4. 建议开发方式

这个项目最适合采用“两段式启动”：

### 第一段：无云资源阻塞开发

目标：

- 先把页面、类型、状态流和接口骨架搭起来

输出：

- 小程序工程跑通
- 页面可点通
- 本地 mock 数据可演示
- 云函数目录与接口契约明确

### 第二段：接入真实云资源

目标：

- 接 CloudBase
- 接 OCR
- 接鉴权
- 接真实删除与日志

输出：

- 上传到 OCR 再到人工修正形成真实闭环

## 5. 建议推进方式

## 5.1 总体节奏

不按自然周推进时，建议按 `执行批次` 管理。

这样做更适合你当前这种：

- 单人推进
- AI 高参与开发
- 云资源和样本准备可能穿插进行
- 每完成一段就想立刻验收

时间上仍可参考：

- 全职最快 `4 到 5 周`
- 全职稳妥 `6 周`
- 兼职 `8 到 12 周`

但真正执行时，建议只看“当前批次是否完成”，不要死盯周数。

## 5.2 执行批次安排

### 批次 0：启动准备

目标：

- 把正式开发门槛补齐

任务：

- 注册并开通 CloudBase
- 开通 OCR 服务
- 建数据库安全规则
- 确认小程序后台和 AppID
- 准备首批脱敏样本
- 建 Git 仓库
- 初始化工程

交付物：

- 云资源可用
- 小程序项目可跑
- 工程目录已建立

进入下一批次条件：

- CloudBase 可用
- OCR 可调通
- 至少有最小样本集

### 批次 1：基础骨架

目标：

- 完成静态页面与基础数据模型

任务：

- 接入 TypeScript
- 建 `shared/types`
- 搭登录页
- 搭首页
- 搭患者列表页
- 搭患者详情页
- 搭设置与隐私页
- 搭 AI 高级设置页
- 建云函数骨架

交付物：

- 页面骨架可运行
- 类型结构稳定
- 假数据可联调

进入下一批次条件：

- 页面主流程可点通
- 目录和类型结构不再频繁变化

### 批次 2：登录、患者与基础鉴权

目标：

- 跑通用户与患者主链路

任务：

- 接微信登录
- 建 `users` / `patients`
- 实现患者 CRUD
- 接 CloudBase 基础读写
- 初步接入数据库安全规则
- 加操作日志基础能力

交付物：

- 可登录
- 可创建患者
- 数据按用户隔离

进入下一批次条件：

- 患者主链路稳定
- 越权访问被正确拦截

### 批次 3：上传与 OCR

目标：

- 跑通上传和 OCR 主链路

任务：

- 上传图片/PDF
- 接云存储临时区
- 建 `documents`
- 实现 `createDocument`
- 实现 `runOcr`
- 保存 `raw_text`
- 处理上传失败和 OCR 失败状态

交付物：

- 可上传资料
- 可看到 OCR 原文
- 失败态可处理

进入下一批次条件：

- 上传到 OCR 的链路稳定
- OCR 原文可回看

### 批次 4：人工修正、手工补录、AI 高级能力

目标：

- 先把不依赖 LLM 的整理闭环跑通，再补 AI 增强

任务：

- 完成 OCR 确认页
- 保存结构化结果
- 支持人工修正
- 支持手工补录
- 接入 `user_ai_provider_settings`
- 实现 `save/get/disable/delete/testUserAiSettings`
- 接入 `parseMedicalDocument` 的“启用才调用模型”逻辑

交付物：

- 用户可手工整理资料
- 已启用自定义模型的用户可触发结构化提取

进入下一批次条件：

- 未启用 AI 时可完整手工闭环
- 已启用 AI 时可成功返回结构化结果

### 批次 5：时间线、用药、摘要、删除

目标：

- 把“资料 -> 输出结果”做完整

任务：

- 建时间线生成逻辑
- 建用药记录生成逻辑
- 建固定模板摘要
- 实现软删除
- 实现删除联动重建
- 增加隐私说明页的实际能力入口

交付物：

- 时间线可看
- 用药记录可维护
- 摘要可生成
- 删除可闭环

进入下一批次条件：

- 关键业务输出页都能正常使用
- 删除联动无明显错乱

### 批次 6：测试、灰度与修正

目标：

- 把首版打磨到能试用

任务：

- 按测试模板执行回归
- 修关键 bug
- 补空状态、失败状态、加载状态
- 跑一轮脱敏样本测试
- 邀请种子用户试用
- 收集反馈并调整

交付物：

- 可试用首版
- 有首轮真实反馈

完成标志：

- 种子用户能走通核心闭环
- 没有阻塞级安全问题和数据错乱问题

## 6. 从现在开始最值得做的批次顺序

如果从现在开始，我建议按下面顺序推进：

### 先立即做

- 创建 Git 仓库
- 初始化小程序项目
- 建目录结构
- 接 TypeScript
- 建 `shared/types`
- 先搭 4 个页面：
  - 登录页
  - 患者列表页
  - 患者详情页
  - 设置与隐私页

这部分对应：

- 批次 1

### 再补环境与样本

- 开通 CloudBase
- 开通 OCR
- 配置环境变量
- 建数据库集合
- 配置安全规则
- 准备脱敏样本

这部分对应：

- 批次 0

### 然后进入主线开发

- 接微信登录
- 接患者 CRUD
- 跑上传与 OCR
- 再接手工修正和 AI 高级设置

这部分对应：

- 批次 2
- 批次 3
- 批次 4

## 7. 开工门槛建议

我建议把“可以开始写代码”和“可以进入正式主开发”分开看。

### 7.1 可以开始写代码的门槛

满足下面任意一组就可以开工：

- 页面、类型、接口骨架已定
- 你已经确定用微信原生 + CloudBase + OCR

这两个条件你现在已经满足了。

### 7.2 可以进入正式主开发的门槛

下面 4 条都满足后，再进入完整联调：

- CloudBase 环境可用
- OCR 服务可用
- 安全规则已配置
- 样本资料已准备

## 8. 需要你特别注意的节奏点

### 8.1 不要一开始就做的事

- 不要先做 AI 问答
- 不要先做复杂规则引擎
- 不要先做多端适配
- 不要先做公开上线准备

### 8.2 最应该先守住的事

- 用户隔离
- OCR 原文可回看
- 人工修正权
- 软删除
- 失败兜底

## 9. 最终判断

我的建议很明确：

- `现在就可以开始工程开发`
- `1 到 3 天内补齐云资源和样本后，再正式进入主线开发`
