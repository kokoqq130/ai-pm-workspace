# 慢病病例管理小程序技术架构与开发计划

## 1. 项目定位

### 1.1 产品一句话

一个帮助慢病患者或家属，将分散的病历、检查单和长期用药记录整理成清晰时间线和就诊摘要的微信小程序。

### 1.2 首版目标

用最小成本验证 3 件事：

- 用户是否愿意上传和整理真实病例资料
- 用户是否愿意长期维护病例时间线和用药记录
- 用户是否会在换医生、复诊、陪诊前主动打开产品

### 1.3 首版边界

本期包含：

- 微信登录
- 患者档案
- 资料上传
- OCR 识别
- OCR 结果人工修正
- 病例时间线
- 长期用药记录
- 就诊摘要

本期不包含：

- AI 诊断
- 治疗建议
- 用药调整建议
- 在线问诊
- 支付系统
- 广告系统
- 多端同步之外的平台版本

## 2. 技术架构

### 2.1 总体架构

```text
微信小程序前端
  -> 微信登录
  -> 上传病历图片/PDF
  -> 调用云函数

腾讯云 CloudBase
  -> 云函数：登录态处理 / OCR 调用 / LLM结构化提取 / 摘要生成 / 数据清洗 / 鉴权
  -> 云数据库：用户、患者、病历条目、时间线、用药记录、摘要
  -> 云存储：原始文件短期中转

腾讯云 OCR
  -> 图片/PDF 文字识别
  -> 返回纯文本或基础文本块

LLM Extraction Provider
  -> 根据 OCR 文本输出标准化 JSON
  -> 支持后续切换不同模型服务商
```

### 2.2 推荐技术栈

前端：

- 微信小程序原生开发
- TypeScript
- 小程序原生组件 + 自定义组件

云端：

- 腾讯云 CloudBase
- 云函数运行时：Node.js
- 云数据库
- 云存储

OCR：

- 腾讯云 OCR API
- 阿里云 OCR 作为备选方案

结构化提取：

- 首版建议由 LLM 完成 OCR 文本到结构化 JSON 的提取
- 不建议首版以大量正则和规则作为主方案

开发辅助：

- AI 代码生成/重构/测试辅助
- GitHub 版本管理

类型设计建议：

- 前后端共享一套核心领域 TS 类型
- 数据库记录类型由云函数侧维护
- 页面展示类型由前端单独维护

后端语言结论：

- 首版主后端推荐 `Node.js`
- 不建议首版主后端直接采用 Python
- 如果后续自建 OCR、文档解析或模型推理服务，再单独引入 Python 服务

### 2.3 为什么优先选微信原生

- 当前只做微信一个平台
- 原生能力最完整
- 调试、上传、权限、文件链路最直接
- 对 MVP 最省心

后续如果确认要扩展 H5 或 App，再评估迁移到 Taro。

### 2.4 为什么主后端优先选 Node.js

- 当前主后端职责主要是登录、文件流程、OCR 调用、数据入库和摘要编排
- 这些能力更偏 API/BFF 与业务编排，不是重模型推理
- Node.js 更适合当前的小程序 + CloudBase + TypeScript 组合
- 更适合前后端共享核心类型
- 更适合 AI 辅助快速生成云函数和 CRUD 代码

### 2.5 Python 的角色定位

当前不建议让 Python 作为首版主后端。

后续只有在以下场景出现时，再考虑引入 Python：

- 自建 OCR 服务
- 自建医学文本抽取服务
- 私有化模型推理
- 复杂文档解析流水线

推荐演进方式：

- 主后端继续使用 Node.js
- 将 OCR/AI 能力抽象为独立 provider
- 未来如有必要，再把 provider 背后替换为 Python 服务

## 3. 核心模块设计

### 3.1 用户与登录

方案：

- 小程序调用 `wx.login()`
- 云函数通过微信接口换取 `openid`
- 使用 `openid` 作为系统内唯一用户标识

首版不做：

- 账号密码
- 邮箱登录
- 独立手机号体系

可选增强：

- 后续加入手机号绑定
- 加入家庭成员协作关系

### 3.2 患者档案

每个用户可维护多个患者档案，例如：

- 自己
- 父母
- 配偶
- 孩子

患者档案字段建议：

- patient_id
- owner_openid
- 姓名或昵称
- 性别
- 出生年份
- 主要疾病标签
- 过敏史
- 备注
- 创建时间
- 更新时间

### 3.3 资料上传

支持上传：

- 病历照片
- 检查报告图片
- 处方单图片
- PDF 文档
- 出院小结

上传流程：

1. 用户选择患者档案
2. 用户上传图片或 PDF
3. 文件进入云存储临时区
4. 创建资料记录并进入 `processing` 状态
5. 触发 OCR 云函数

### 3.4 OCR 识别链路

建议流程：

1. 云函数读取临时文件
2. 调用腾讯云 OCR API
3. 返回 OCR 原始文本
4. 调用 LLM 结构化提取服务
5. 由 LLM 按约定 JSON Schema 返回结构化结果
6. 写入数据库
7. 更新资料状态为 `recognized`

说明：

- 首版不建议自己在 Node.js 中堆大量正则做医学字段解析
- 首版建议将 Node.js 作为编排层，由 LLM 负责结构化提取
- 最终结果仍需允许用户手动修正

### 3.5 LLM 结构化提取策略

推荐链路：

1. OCR 输出原始文本
2. 云函数构造标准 Prompt
3. 调用 LLM
4. 要求返回固定 JSON
5. 后端做 JSON 校验与兜底
6. 再写入 `document_ocr_results.structured_json`

推荐要求：

- 必须要求模型只返回 JSON
- 必须对返回结构做 schema 校验
- 必须允许字段缺失，不允许模型瞎编
- 关键字段依然允许用户手工修正

### 3.6 LLM Provider 设计建议

建议在后端增加 `extractionProvider` 抽象层，而不是把某家模型接口直接写死在业务里。

推荐统一输出字段：

- `docType`
- `docDate`
- `hospitalName`
- `departmentName`
- `diagnosisKeywords`
- `medications`
- `examItems`
- `summary`

这样后续无论底层接：

- 你自己的默认模型
- 用户自填 API Key 的模型
- 后续自建 Python OCR/AI 服务

都不需要重写上层业务逻辑

### 3.7 数据结构化

OCR 后至少提取以下字段：

- 文档类型
- 文档日期
- 医院名称
- 科室
- 诊断关键词
- 药物名称
- 检查项目
- 检查结果摘要

结构化结果写入后，供以下模块使用：

- 病例时间线
- 用药记录
- 就诊摘要
- 后续 AI 资料问答

### 3.8 病例时间线

时间线按日期聚合病例事件，包括：

- 就诊记录
- 检查记录
- 用药变化
- 住院/出院
- 手术记录

展示目标：

- 让用户自己快速回顾
- 让医生在 1 到 3 分钟内看懂病程

### 3.9 用药记录

记录字段建议：

- 药名
- 剂量
- 频次
- 开始时间
- 结束时间
- 适应症
- 停药/换药原因
- 来源文档

### 3.10 就诊摘要

首版摘要建议固定模板生成，不必一开始做自由问答。

摘要包含：

- 当前主要疾病
- 重要既往病史
- 目前正在使用的药物
- 最近重要检查结果
- 最近 3 到 6 个月的关键变化
- 本次就诊建议携带的资料

首版分享边界：

- 支持复制文本
- 不要求首版支持 PDF 导出
- 不要求首版支持图片分享

## 4. 数据与存储策略

### 4.1 推荐策略

- 原始文件：云端短期保存
- 结构化结果：云端长期保存
- 前端：仅做缓存，不做唯一数据源

### 4.2 为什么不建议纯本地

- 小程序本地存储不适合长期病例库
- 换手机、清缓存、重装微信会有数据丢失风险
- 结构化结果需要支持长期演化和后续 AI 能力

### 4.3 文件保留建议

- 默认保留原始文件 3 天
- OCR 失败可重试
- 用户可手动删除原始文件
- 后续可增加“永久保留原文件”开关

### 4.4 删除一致性策略

- 首版建议核心业务表采用软删除而不是直接硬删除
- 删除单份资料后，先标记删除，再重建相关时间线和摘要
- 删除患者档案后，先标记患者及关联数据删除状态
- 物理删除可作为后续清理任务异步执行

### 4.5 数据隔离与安全规则

本项目处理高敏感健康信息，必须采用后端和数据库双层数据隔离。

要求：

- 不允许只依赖前端传入的 `patientId` / `userId` 做鉴权
- 所有云函数必须从登录上下文重新获取当前用户身份
- 所有用户数据查询必须校验当前用户是否拥有该患者或资料
- CloudBase 数据库层应配置安全规则

推荐安全规则原则：

- `read` / `write` 必须满足当前登录身份等于文档所属人
- 推荐核心业务文档包含 `owner_openid`
- 安全规则按 `auth.openid == doc.owner_openid` 进行限制

### 4.6 用户自填 API Key 的使用建议

如果后续要支持“用户自己填写模型 API Key”，建议把它作为可选高级能力，而不是首版核心依赖。

推荐使用方式：

- 用户在设置页手动填写模型服务商与 API Key
- 前端把 Key 仅提交给你自己的云函数
- 后端在服务端使用该 Key 调用模型
- 前端不直接拿 Key 调模型接口
- 用户首次启用前必须看到明确提示：
  - 启用后，选中的 OCR 文本可能发送到你指定的第三方模型服务商
  - 该能力仅用于结构化提取或资料问答

推荐实现顺序：

1. 灰度阶段先使用平台默认模型配置，先把链路跑通
2. 后续再追加“自定义模型服务”开关
3. 自定义模式下，用户需填写：
   - provider
   - baseUrl
   - model
   - apiKey
4. apiKey 只允许在服务端加密保存或仅本次会话临时使用
5. 前端永远不回显完整 Key，只显示掩码和最后 4 位

推荐后端实现：

- 增加 `user_ai_provider_settings` 配置集合
- 云函数收到保存请求后，用服务端密钥加密 `apiKey`
- `parseMedicalDocument` 按当前 `openid` 读取该用户配置
- 若用户未配置自定义模型，则回退到平台默认 provider
- 若用户关闭 AI 提取，则仅保留 OCR 原文并提示手工整理

推荐产品策略：

- 首版灰度不要强依赖用户自己填 Key，否则上传后闭环会变差
- 更适合做成“高级设置”能力
- 只对明确愿意承担第三方模型调用风险的用户开放

不推荐方式：

- 小程序前端直接使用用户填写的 API Key 请求第三方模型

原因：

- 容易泄露 Key
- 难以控制请求格式
- 对高敏感医疗文本不够安全
- 无法稳定做审计、限流和失败兜底

## 6. 云函数职责

建议至少拆成以下函数：

- `login`
  - 接收 `code`
  - 换取 `openid`
  - 创建或更新用户

- `createDocument`
  - 创建资料记录
  - 标记待 OCR 状态

- `runOcr`
  - 读取临时文件
  - 调用 OCR API
  - 写入识别结果

- `parseMedicalDocument`
  - 调用 LLM 提取结构化字段
  - 校验输出 JSON

- `authorizeResource`
  - 校验当前 openid 是否有权访问 patient/document

- `rebuildTimeline`
  - 根据结构化结果重建病例时间线

- `generateVisitSummary`
  - 根据患者资料生成固定格式摘要

- `createManualRecord`
  - 在 OCR 失败时手工补录简版病例记录

- `cleanupTempFiles`
  - 清理过期原始文件

## 8. AI 主导开发方式

你计划全程以 AI 为主，这个项目非常适合采用“AI 生成 + 人工验收”的模式。

### 8.1 建议原则

- AI 负责脚手架、重复代码、基础 CRUD、云函数模板、类型定义、测试样例
- 人工负责范围控制、数据模型确认、交互验收、隐私边界和上线前检查
- 任何涉及医疗语义判断的逻辑，都必须人工 review

### 8.2 推荐开发流

1. 先由 AI 生成数据模型和接口草图
2. 再由 AI 分模块生成页面和云函数
3. 每完成一个模块，立即手测并修订提示词
4. 把 AI 产出的代码再次交给 AI 做 review 和补测试
5. 关键流程保留人工验收清单

### 8.3 AI 适合优先处理的任务

- 数据表定义
- 页面骨架
- 表单与列表组件
- 上传和状态管理
- OCR 结果解析基础逻辑
- 时间线生成逻辑
- 文档与注释
- 测试清单

### 8.4 AI 不应直接决定的事项

- 医疗场景边界文案
- 隐私政策关键措辞
- 错误医学结论的处理方式
- 上线前是否可提审

## 9. 开发计划

## 9.1 周期估算

按单人开发、AI 高参与度估算：

- 全职：4 到 6 周
- 兼职：8 到 12 周

建议按 6 周排期，更稳。

## 9.2 六周开发计划

### 第 0 周：上线前置确认

- 确认小程序主体和类目是否可走当前定位
- 确认隐私政策和敏感信息处理边界
- 注册并配置腾讯云 CloudBase 环境
- 确认 OCR 接口账号和密钥管理方案
- 输出首版信息架构和页面草图

### 第 1 周：项目初始化

- 初始化小程序工程
- 建立基础目录和组件规范
- 接入 TypeScript
- 完成微信登录
- 建立基础数据库集合
- 完成患者档案 CRUD

交付物：

- 可登录
- 可创建患者
- 数据可正常落库

### 第 2 周：资料上传与文件链路

- 完成图片/PDF 选择与上传
- 接入云存储临时区
- 创建 documents 记录
- 完成上传状态机
- 完成基础错误处理

交付物：

- 可上传资料
- 可查看上传状态

### 第 3 周：OCR 与结果确认

- 接入腾讯云 OCR
- 实现 `runOcr` 云函数
- 建立 OCR 结果集合
- 完成 OCR 结果确认和编辑页
- 支持用户修正关键信息
- 增加 OCR 失败后的手工补录兜底
- 接入 LLM 结构化提取链路

交付物：

- 可识别
- 可查看 OCR 文本
- 可人工修正

### 第 4 周：时间线与用药记录

- 实现结构化解析
- 构建病例时间线页面
- 构建用药记录页面
- 支持从 OCR 结果生成时间线事件
- 支持人工补充和编辑

交付物：

- 可查看病例时间线
- 可查看和维护用药记录

### 第 5 周：就诊摘要与隐私能力

- 实现固定模板摘要生成
- 完成患者摘要页
- 增加删除资料和清理逻辑
- 增加隐私说明、数据删除说明
- 增加基础操作日志

交付物：

- 可生成就诊摘要

## 10. 成本估算

以下为基于 2026-03-30 官方资料的粗估，实际费用以购买页为准。

### 10.1 开发期

- CloudBase：0 到 19.9 元/月
- OCR：0 到 20 元/月
- 合计：0 到 40 元/月

说明：

- 开发期调用量低，OCR 常常落在免费额度或极低成本区间

### 10.2 上线后早期验证期

假设：

- 20 到 50 个种子用户
- 每月 OCR 500 到 3000 页

估算：

- CloudBase：19.9 元/月
- OCR：0 到 33 元/月
- 其他存储/调用预留：0 到 20 元/月
- 合计：20 到 70 元/月

### 10.3 略有增长后

假设：

- 约 100 个活跃用户
- 每月 OCR 10000 页

估算：

- OCR 约 110 元/月
- CloudBase 约 19.9 元/月
- 其他预留 20 到 50 元/月
- 合计：130 到 180 元/月

### 10.4 目前不纳入的成本

- 你自己的时间成本
- 法务和隐私文档外包
- 医疗类目咨询成本
- 商业化后的支付和广告系统

## 11. 上线前检查清单

- 小程序主体和类目确认
- 备案要求确认
- 隐私政策完成
- 用户授权文案完成
- 数据删除流程完成
- 文件保留策略完成
- OCR 失败重试机制完成
- OCR 失败手工补录流程完成
- 数据库安全规则完成
- 高敏感信息访问日志具备基础记录
- 产品文案不涉及诊断或治疗建议

## 12. 下一步建议

最建议立即开始的动作：

1. 先确定首版页面和数据结构，不要先写复杂 AI 问答
2. 先把“上传 -> OCR -> 修正 -> 时间线 -> 摘要”闭环跑通
3. 找 3 到 5 个真实慢病家庭做试用反馈
4. 根据真实资料质量，再决定是否强化 OCR、摘要和 AI 问答
