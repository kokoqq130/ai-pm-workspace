# 慢病病例管理小程序 PRD

## 1. Executive Summary

本项目是一款面向慢病患者及其家属的微信小程序，目标是帮助用户将分散在相册、聊天记录、PDF 和纸质资料中的病历、检查单与长期用药信息整理为清晰的病例时间线和就诊摘要，降低换医生、复诊、陪诊场景中的沟通成本。

首版聚焦“上传资料 -> OCR 识别 -> 人工修正 -> 时间线整理 -> 就诊摘要”这一核心闭环，不做诊断或治疗建议，优先验证真实用户是否会持续上传和复用病历资料。

## 2. Problem Statement

### 2.1 谁遇到这个问题

- 慢性病患者本人
- 负责照护、陪诊、整理资料的家属
- 经常跨医院、跨医生复诊的人群

### 2.2 具体问题是什么

用户的病历资料通常分散在多个地方：

- 手机相册中的检查单和处方照片
- 微信聊天里转发的病历截图
- PDF 版检查报告和出院小结
- 纸质病历和手写记录

当用户需要复诊、换医生或向新医生介绍病情时，很难在短时间内把这些资料讲清楚。

### 2.3 为什么痛

- 用户需要在就诊现场临时翻找资料，焦虑感强
- 重要病史、长期用药和关键异常指标容易遗漏
- 家属帮忙整理资料时，缺少统一的时间线和摘要
- 医生很难在短时间内理解患者过去较长时间的病情演变

### 2.4 问题陈述

慢病患者或家属需要一种方式，把长期积累且分散的病历、检查单和用药信息快速整理成清晰摘要，因为现有资料过于碎片化、时间跨度长、就诊时又很难现场讲清楚，这会让人焦虑、慌乱，也容易遗漏关键信息。

## 3. Target Users

### 3.1 Primary Persona

`慢病家属管理者`

特征：

- 30 到 55 岁
- 常用微信
- 负责帮父母、配偶或孩子整理病历
- 不一定懂医疗术语，但愿意花时间把资料整理清楚
- 更关注“关键时刻能不能快速拿出来用”

目标：

- 帮家人把病历讲清楚
- 记录长期用药和检查变化
- 复诊前快速准备材料

### 3.2 Secondary Persona

`慢病患者本人`

特征：

- 长期复诊
- 手里有很多检查结果和处方记录
- 希望自己能看清病情变化

目标：

- 梳理自己的病情发展
- 减少复诊沟通负担
- 让医生快速理解过去情况

## 4. Why Now

- 用户资料越来越多，手工整理门槛高
- OCR 与轻量 AI 摘要能力已经足够支持首版
- 微信小程序降低了用户使用门槛
- 本项目不需要先做重 SaaS 和复杂部署，可先验证真实需求

## 5. Product Goals

首版目标：

- 让用户可以上传病例资料并完成 OCR 识别
- 让用户可以把识别结果修正为可信的结构化信息
- 让用户可以按时间线查看病程和用药变化
- 让用户可以一键生成“给医生看”的就诊摘要

## 6. Success Metrics

### 6.1 Primary Metrics

- 首次使用用户完成至少 1 次资料上传的比例，目标 `>= 60%`
- 上传后完成 OCR 确认的比例，目标 `>= 70%`
- 生成过至少 1 次就诊摘要的用户比例，目标 `>= 40%`

### 6.2 Secondary Metrics

- 单用户平均录入资料数，目标 `>= 3`
- 单用户创建患者档案数，目标 `>= 1`
- 7 天内二次打开率，目标 `>= 30%`
- 30 天内复用率，目标 `>= 20%`

### 6.3 Qualitative Metrics

- 用户是否认为“整理病历更省事了”
- 用户是否在复诊前主动使用该工具
- 用户是否认为摘要真的能帮助医生快速理解病情

### 6.4 首轮验证周期

- 首轮验证建议周期：`2 周`
- 首批种子用户建议人数：`3 到 5 人`
- 验证方式：基于真实或脱敏资料完成至少 1 次完整闭环

## 7. Solution Overview

### 7.1 首版解决方案

产品通过微信小程序提供以下闭环：

1. 微信登录
2. 创建患者档案
3. 上传病历图片或 PDF
4. 调用 OCR 识别资料内容
5. 用户确认和修正关键字段
6. 自动生成病例时间线与用药记录
7. 生成就诊摘要

### 7.2 产品原则

- 优先解决“整理和表达病情”，不做诊断
- 优先让结果可校正，不追求一开始 100% 自动化
- 优先确保资料结构化，可支持后续 AI 问答
- 优先做轻量、可信和可复用的流程
- OCR 之后的结构化提取优先使用 LLM，不以复杂规则引擎为首版主方案

## 8. Scope

### 8.1 In Scope

- 微信登录
- 患者档案管理
- 病历图片/PDF 上传
- OCR 识别
- OCR 结果人工修正
- 病例时间线
- 用药记录
- 就诊摘要
- 删除资料和基础隐私说明

### 8.2 Out of Scope

- AI 诊断
- 治疗建议
- 药物调整建议
- 在线问诊
- 医院系统对接
- 桌面端 / App / H5 多端同步开发
- 支付与广告系统

## 9. Functional Requirements

### 9.1 登录与用户

- 用户应可通过微信登录进入系统
- 系统应基于 `openid` 建立用户记录
- 每个用户应只能访问自己的患者资料

### 9.2 患者档案

- 用户应可创建多个患者档案
- 患者档案应支持基础信息和疾病标签
- 用户应可编辑和删除患者档案

### 9.3 资料上传

- 用户应可上传图片和 PDF
- 资料需绑定到具体患者档案
- 上传后应有状态显示：待处理、处理中、已完成、失败

### 9.4 OCR 识别

- 系统应对上传资料执行 OCR
- 系统应保存原始 OCR 文本
- 系统应提取初步结构化字段
- 结构化字段首版应优先通过 LLM 提取
- 后端必须对 LLM 返回的 JSON 做校验

### 9.5 人工修正

- 用户应可编辑识别出的关键字段
- 修改后应重新更新结构化结果
- 修改记录应保留更新时间

### 9.6 病例时间线

- 系统应按时间展示病例事件
- 时间线应支持展示来源文档
- 时间线事件应可由 OCR 结果自动生成

### 9.7 用药记录

- 系统应支持展示药品名称、剂量、频次、起止时间
- 用户应可手动补充或修正用药记录

### 9.8 就诊摘要

- 系统应支持按固定模板生成摘要
- 摘要应覆盖主要疾病、既往病史、当前用药、近期检查结果
- 首版摘要应支持文本复制
- 首版不强制提供 PDF 导出或图片分享

### 9.9 数据安全与隔离

- 后端不得只依赖前端传入的 `patientId` 或 `userId` 进行鉴权
- 所有数据查询与写入必须在后端按当前登录身份重新校验
- 数据库层应配置基于用户归属的安全规则

## 10. User Stories

### Story 1

作为一名慢病家属，我希望能为家人创建一个患者档案，这样我就能把后续所有病历资料放到同一个地方管理。

Acceptance Criteria:

- [ ] 可以创建患者档案
- [ ] 可以填写基础信息
- [ ] 可以从患者列表进入详情页

### Story 2

作为一名长期陪诊的家属，我希望上传病历照片或 PDF 后系统能自动识别内容，这样我不需要手动逐条录入。

Acceptance Criteria:

- [ ] 支持图片和 PDF 上传
- [ ] 上传后能触发 OCR
- [ ] OCR 完成后能看到原始文本和关键字段

### Story 3

作为用户，我希望能修正识别错误的内容，这样系统整理出的时间线和摘要更可信。

Acceptance Criteria:

- [ ] 可编辑日期、医院、诊断、药名等字段
- [ ] 修改后保存成功
- [ ] 修改结果同步影响时间线和摘要

### Story 4

作为用户，我希望系统能自动生成病例时间线，这样我能快速回顾病程变化。

Acceptance Criteria:

- [ ] 时间线按日期倒序展示
- [ ] 每条事件能查看来源文档
- [ ] 时间线支持就诊、检查、用药、住院等类型

### Story 5

作为用户，我希望一键生成给医生看的就诊摘要，这样换医生或复诊时可以快速说明情况。

Acceptance Criteria:

- [ ] 能生成固定模板摘要
- [ ] 摘要包含当前病情、用药和近期检查结果
- [ ] 摘要可复制

### Story 6

作为用户，我希望在 OCR 失败时仍然能补录一份简版病历记录，这样我的病例时间线不会因为识别失败而中断。

Acceptance Criteria:

- [ ] OCR 失败后可进入手工补录流程
- [ ] 可填写最少字段：日期、文档类型、诊断/药物摘要
- [ ] 手工补录结果可进入时间线

### Story 7

作为用户，我希望删除资料后相关数据能被一致处理，这样不会出现已经删除的资料仍然影响时间线和摘要。

Acceptance Criteria:

- [ ] 删除单份资料后同步删除该资料关联的 OCR 结果
- [ ] 删除单份资料后更新相关时间线和摘要
- [ ] 删除患者档案前给出完整影响提示

## 11. Non-Functional Requirements

- 关键页面首次加载应尽量控制在可接受范围内
- OCR 处理失败应有明确提示和重试机制
- 用户资料访问必须按用户隔离
- 敏感信息相关操作应有基础日志记录
- 产品文案不得暗示诊断或替代医生判断
- 所有删除操作必须有二次确认
- 原始文件应有明确保留期限和自动清理机制

## 12. Dependencies

- 微信小程序主体与类目
- CloudBase 环境
- 腾讯云 OCR 服务
- 隐私政策和用户授权文案
- 基础测试设备和真实样本资料

## 13. Risks

- 医疗相关审核边界不清导致提审受阻
- OCR 对复杂版式病历识别效果不稳定
- 用户对云端中转敏感医疗资料有顾虑
- 首版功能范围扩大导致延期
- AI 自动生成代码质量参差不齐，需要人工复核

## 14. Open Questions

- 原始文件默认保留多久最合适
- 首版是否允许创建多个家庭成员协作关系

## 15. 数据保留与删除规则

### 15.1 原始文件保留

- 原始文件默认保留 `3 天`
- 用于 OCR 失败重试和人工复核
- 到期后自动清理

### 15.2 长期保存内容

- 患者档案
- OCR 原始文本
- 结构化结果
- 时间线事件
- 用药记录
- 就诊摘要

### 15.3 删除单份资料时

- 首版建议优先软删除
- 删除资料记录
- 删除关联 OCR 结果
- 重新计算该患者时间线
- 重新计算该患者摘要基础数据

### 15.4 删除患者档案时

- 建议优先软删除患者及其关联核心数据
- 删除患者档案及其关联资料
- 删除关联 OCR 结果
- 删除时间线、用药记录、摘要

## 16. OCR 失败兜底策略

- 首版允许手工补录简版记录
- 手工补录最少字段：
  - 日期
  - 文档类型
  - 诊断或事件摘要
  - 可选药物信息
- 手工补录内容可进入时间线
- 对低置信度或手写病历，应明确提示用户优先手工提炼关键信息

## 17. LLM 提取与用户自填 API Key 策略

- 首版结构化提取建议采用“OCR 文本 -> LLM -> JSON”链路
- Node.js 负责调度 OCR、调用 LLM、校验 JSON 和入库
- 不建议首版在前端直接用用户填写的 API Key 调模型
- 如果后续支持用户自填 API Key，应由后端代调用，并在启用前明确提示第三方模型服务商的数据处理风险

## 18. 首版上线策略

- 首版建议先灰度给 `3 到 5` 位熟人或种子用户
- 不建议一开始直接公开上线
- 第一轮重点收集：
  - OCR 识别质量
  - 时间线是否好用
  - 摘要是否真实帮助就诊沟通
- 在灰度验证后再决定是否公开发布
## 19. Milestones

- 里程碑 1：登录、患者档案、数据库初始化完成
- 里程碑 2：上传 + OCR 基础链路跑通
- 里程碑 3：时间线和用药记录可用
- 里程碑 4：就诊摘要与隐私流程闭环
- 里程碑 5：灰度测试与种子用户验证
